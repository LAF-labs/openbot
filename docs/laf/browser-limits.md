# 봇의 브라우저가 못 하는 것 — 그리고 실제로 되는 것

봇은 컨테이너 안의 크로미움 하나를 몬다(`agent-computer`). 사람이 쓰는 브라우저와
거의 같지만, **구조적으로 안 되는 일**이 있다. 안 되는 것을 적어 두는 편이,
안 되는 줄 모르고 시키는 것보다 낫다.

아래 숫자는 전부 **실측**이다. 사이트 표는 2026-09-03에 손으로 한 번 잰 것이고,
픽스처 표는 `agent-computer/tests/korean-sites.test.ts`가 매번 다시 잰다.

---

## 1. 안 되는 것 — 사람에게 넘겨야 한다

| 무엇 | 왜 | 봇이 해야 하는 일 |
|---|---|---|
| **공동인증서·금융인증서 로그인** | 인증서는 사람의 기기(또는 USB·클라우드 저장소)에 있고, 브라우저 밖 프로그램이 서명한다. 컨테이너에는 그 프로그램도 인증서도 없다. | `computer_request_help`로 사람에게 인계 |
| **보안키패드(마우스로 누르는 숫자판)** | 은행·카드사가 키 입력을 가로채지 못하게 만든 것이다. 자동 입력을 막는 것이 그 물건의 목적이므로, 우회하면 안 되고 되지도 않는다. | 인계 |
| **캡차(CAPTCHA)** | 사람인지 확인하는 장치다. 봇이 통과하려 해서는 안 된다. | 인계 |
| **결제 인증창 / 간편결제 비밀번호** | 대개 별도 창이거나 앱으로 넘어가고, 승인은 사람의 판단이다. | 인계 |
| **`확인/취소` 창의 '확인' 누르기** | 브라우저가 띄우는 `confirm`은 봇이 대신 누르지 않는다. 내용은 `laf:dialog`로 알려 주고 **취소**를 누른다. `정말 삭제하시겠습니까?`에 예라고 답하는 것은 사람의 자리다. | 인계 |
| **휴대폰 본인인증 / 문자 인증번호** | 문자는 사람의 폰으로 온다. | 칸 하나면 `computer_request_secret`, 여러 단계면 인계 |
| **카메라·마이크·파일 탐색기 열기** | 컨테이너에 장치가 없다. 파일은 봇의 작업 공간에서만 올린다(`computer_upload_file`). | 필요한 파일을 먼저 작업 공간에 두기 |
| **1MB를 넘는 파일 내려받기** | 작업 공간 쓰기 한도와 같은 값이다. 넘으면 저장하지 않고 지운 뒤 `laf:download_too_large`로 알린다. | 사람이 직접 받기 |

### 조심할 것 하나 — 쿠키는 볼륨에 평문에 가깝게 있다

컨테이너에는 데스크톱의 키링이 없어서 크로미움을 `--password-store=basic`으로
띄운다. 로그인 쿠키는 `agent-profiles` 볼륨을 읽을 수 있으면 읽힌다. **1인 1VM**
(`deployment-model.md`)이기 때문에 감수하는 것이고, 볼륨 권한이 곧 그 경계다.
여러 사람이 한 VM을 쓰는 구성으로 바꾸면 이 문장이 먼저 거짓이 된다.

### 조심할 것 둘 — 봇들은 로그인을 나눠 쓴다 (2026-09-16)

프로파일은 **배포에 하나**다. 한 봇이 로그인한 사이트는 다른 봇들도 로그인된
상태이고, 프로파일은 그것을 막지 않는다 — 막는 것은 앞단의 경계뿐이다. 결정과
그 대가는 `deployment-model.md`의 해당 절에 있다. 여기서 실무에 닿는 것 셋:

- **초기화는 봇 전부를 로그아웃시킨다.** 누가 눌렀든 지워지는 것은 공용 프로파일
  하나이고, 업그레이드 때 남겨 둔 옛 봇별 프로파일들도 같이 지운다.
- **봇을 지워도 로그인은 남는다.** 아래 목록의 그 줄이 2026-09-16에 바뀌었다.
- **봇별 프록시(`EGRESS_PROXY_<BOT>`)는 더 이상 걸리지 않는다.** 브라우저가
  하나이므로 프록시도 하나다(`EGRESS_PROXY_DEFAULT`). 봇별 변수가 남아 있으면
  부팅 로그가 무시했다고 말한다.

## 2. 되는 것 — 무엇이 어떻게 되는가

- **한국어로 뜬다.** 로케일 `ko-KR`, 시간대 `BOT_TIME_ZONE`(기본 `Asia/Seoul`).
  실측: 고치기 전에는 `navigator.language`가 `en-US@posix`, 시간대가 `UTC`였다.
- **UA 문자열에는 헤드리스 표식이 없다 — 그러나 헤더에는 있다.** UA 문자열에서는
  `HeadlessChrome`이 사라졌고(→ `Chrome/151.0.0.0`, 크롬이 스스로 쓰는 형식 그대로), 자동화 티가
  가장 싸게 나는 신호 하나를 없앤 것이지 탐지를 뚫는 것이 아니다. **실측(2026-10-04): 모든 HTTPS
  요청의 `Sec-Ch-Ua` 헤더와 페이지의 `navigator.userAgentData`는 여전히 `"HeadlessChrome";v="151"`을
  말한다.** Playwright의 UA 덮어쓰기는 문자열에만 닿고 브랜드 목록에는 닿지 않는다. 이 문서가 한 달
  동안 "표식이 없다"고 적은 것은 틀렸다. 또 2026-10-04까지는 빌드번호를 전부 적은
  문자열(`Chrome/151.0.7922.34`)을 보냈는데, 어떤 크롬도 UA에 빌드번호를 적지 않으므로 그것 자체가
  표식이었다 — 쿠팡 판매자센터는 그 문자열을 단 진짜 크롬도 3/3 거부했고, 0으로 채운 형식은 3/3
  열었다. 남은 표식까지 없애는 길은 표식이 없는 브라우저(새 헤드리스 또는 화면 있는 풀 Chromium)뿐이며,
  측정과 권고는 `~/laf/docs/bot-browser-choice-2026-10-04.md`에 있다. 위장(지문·GPU 스푸핑)은 하지 않는다.
- **새 탭을 따라간다.** `target=_blank`로 열린 탭이 곧 봇이 보는 탭이 되고,
  스냅샷의 `tabs`에 전부 나온다. `computer_switch_tab`으로 옮긴다.
- **경고창을 듣는다.** `alert`은 확인을 눌러 주고, `confirm`·`prompt`는 취소를
  누른 뒤 **내용을 그대로** 다음 툴 결과에 실어 준다(`laf:dialog`).
- **내려받고 올린다.** 내려받은 파일은 `작업공간/downloads/`에 이름 그대로
  저장된다(같은 이름은 `(2)`가 붙는다). 올릴 때는 작업 공간 안의 파일만 된다.
- **iframe 안을 읽는다.** 같은 출처의 iframe 본문은 페이지 본문에 합쳐지고,
  **그 안의 버튼도 눌린다** — 실측: 스냅샷이 프레임 안 버튼을 `f1e4` 같은 ref로
  주고, 그 ref로 클릭이 실제로 동작했다. 못 읽는 프레임은 `laf:frame_opaque`로
  알린다(결제창·인증창이 대개 그렇다).
- **기사면 본문만, 아니면 전부 읽는다**(`agent-computer/src/reader.ts`). 네이버 뉴스 한 면의 글자는
  대부분 메뉴·랭킹·댓글이라 6,000자 안에 기사가 몇 줄 안 들어갔고, 그래서 스스로 기사라고 밝힌
  페이지는 Readability(Firefox 읽기 모드의 엔진)가 고른 본문만 읽고 `reader: true`를 단다. **고른
  것이 본문이 아니면 전부 읽는다**(2026-10-04): 페이지 글자가 1,500자 미만일 때, 고른 것의 80% 이상이
  링크 글자일 때(메뉴), 스스로 기사라고 밝히지 않고(`og:type`·JSON-LD 없이) `<article>` 요소만
  있는 페이지에서 고른 것의 절반 이상이 그 요소 밖에 있을 때(상품 카드만 `<article>`이고 고른 것은
  푸터). 스스로 기사라고 밝힌 페이지는 이 셋째 규칙을 받지 않는다 — 본문은 `<div>`에 두고 관련 기사
  카드에만 `<article>`을 쓰는 뉴스 페이지가 메뉴부터 통째로 읽히지 않게. 세트에서 이 규칙만이 걸러 낸
  쪽(무신사·질로·삼성·슈피겔 홈)은 전부 요소 말고는 아무 말도 하지 않는 페이지였다. 고른 것의
  생김새로는 가를 수 없었다: 질로의 푸터는 1,249자에 긴 문단뿐이라 세트의 진짜 기사 넷(433~619자)보다
  길고 더 기사답다. 실측(실제 `/navigate`, 전 → 후): 컬리의 없는 상품은 푸터
  631자 → 전부 1,397자("구매가 어려워"가 125자째), 연합뉴스의 없는 기사 주소는 섹션 메뉴 1,614자 →
  전부 3,345~4,000자("원하시는 페이지를 찾을 수 없습니다"가 139자째), 무신사 홈은 푸터 420자 → 전부
  4,432자. 라벨 세트(`evals/page-facts`)에서 기사로 읽히던 25쪽 중 진짜 기사 12쪽(네이버 뉴스 3,
  연합뉴스, 정책브리핑 보도자료, 위키 문서 4, Google·Cloudflare 문서, gov.uk)은 그대로 기사로 읽히고,
  새로 전부 읽히게 된 것은 위 셋과 홈 6곳(정책브리핑·삼성·슈피겔·부산·강남구·한겨레)이다.
  - 남은 것: 질로의 로봇 확인은 403 화면으로 올 때는 전후 모두 그 문장이 읽히지만, 200 홈 위에 뜰
    때는 고친 뒤에도 문장이 없다(푸터 1,520자 → 홈 전체 3,041자). 403 화면에서 "길게 누르기" 단추는
    `about:blank` 프레임 안에 있고, 읽기는 그런 프레임을 건너뛴다 — 200 화면도 같은지는 재지 못했다.
    법제처의 "해당 법령이 존재하지 않습니다"는 그림이라 글자로는 오지 않는다.
- **페이지 스크립트가 읽기를 막아도 읽는다.** 고용24(work24.go.kr, ei.go.kr도 그리로 간다)는 전역
  `Map`을 자바식(`put`·`get`, `set` 없음)으로 바꿔 놓는다. Playwright는 페이지가 돌려준 객체를 그
  페이지의 `Map`으로 세기 때문에 거기서는 모든 객체가 `undefined`로 왔고, `/navigate`가 502
  `laf:browser_failed`로 실패했다(`undefined is not an object (evaluating 'main.read.text')`,
  2026-10-04, 두 주소 각 2/2). 읽기는 이제 문자열로 답한다 → 200, 1,845자. 그래도 막히는 페이지는
  화면 글자를 그대로 읽어 `laf:page_text_plain`을 붙이고, 그것마저 안 되면 빈 글자와 같은 사실을
  준다 — 빈 페이지라는 뜻이 아니다. 같은 페이지의 `/snapshot`은 전후 모두 됐다(요소 87개).
  **페이지 탓으로 치는 것은 둘뿐이다**: 읽기 스크립트가 답을 주지 않았거나, 페이지 자신의
  자바스크립트가 그 안에서 던졌거나(스크립트가 페이지 안에서 잡아 답으로 알린다). 브라우저 쪽 실패 —
  렌더러 크래시, 닫힌 탭, 프로토콜 오류 — 는 전과 같이 502 `laf:browser_failed`이고, 넘어가는 중인
  페이지는 전과 같이 다시 읽는다. 그대로 읽게 될 때마다 로그에 `reader_fell_back` 한 줄이 남는다:
  페이지의 origin과 우리 목록에 있는 오류 이름뿐이고, 주소의 나머지·오류 메시지·페이지 글자는 없다.
- **스냅샷은 15초 안에 답한다**(`SNAPSHOT_DEADLINE_MS`, `agent-computer/src/snapshot.ts`).
  요청은 받고 끝내 답하지 않는 iframe — 멈춘 결제창·인증창 — 이 있어도 봇의 차례를 붙잡지
  않는다. 기다림은 전부 그 안에 든다: 아직 도착 중인 페이지 최대 5초, 비밀 칸 확인 한 번에 1초,
  문서가 아직 없는 프레임 3초. 그때까지 문서가 없는 프레임은 빼고 `opaqueFrames`로 세며, 페이지와
  뜬 프레임의 요소는 그대로 온다. 기다리는 사이에 도착한 프레임의 비밀 칸은 한 번 더 확인해
  표시하고 값을 가린다. 답 없는 프레임이 있는 페이지는 `load`에 영영 닿지 않아서, 볼 때마다
  4초를 먼저 기다린다 — 그런 페이지의 스냅샷이 9초쯤 걸리는 까닭의 절반이 그것이다.
- **넘어가는 중인 탭도 곧바로 답한다**(`agent-computer/src/page-arrival.ts`). 답하지 않는 사이트로
  넘어가는 중인 탭은 새 페이지가 올 때까지 문서가 아무것도 답하지 않는다. 읽기·스냅샷·가리키기는
  1초쯤에, 탭 목록은 곧바로 `laf:page_loading`(가는 곳의 origin만)과 함께 답하고, 스크린샷은 브라우저가
  칠해 둔 떠나는 페이지를 준다. 그런 탭의 제목은 비운다 — Playwright는 제목 자리에 가는 주소 전체를
  줬고, GET 폼은 그 주소에 칸의 값을 넣는다. 읽기 전체는 15초(`READ_DEADLINE_MS`) 안에 끝난다.
- **렌더러가 죽은 탭은 버리고, 봇이 다시 보기 전에는 그 봇의 어떤 행동도 받지 않는다** (2026-10-05,
  `agent-computer/src/tabs.ts` `died`, `tab-loss.ts`). 실측: 봇 하나로 무거운 한국 사이트(네이버
  쇼핑·뉴스) 과제 57개를 돌리던 중 그 봇만 어떤 주소도 열지 못했다 — `laf:navigation_failed` 19번
  연속(사이사이 `laf:browser_failed`), 10분 뒤에도 같았고, 컨테이너는 `healthy`, 로그에는 warn 한 줄
  없고, 다른 이름의 봇은 곧바로 됐다. 재현(`crashed-tab.test.ts`, 그 탭의 렌더러 프로세스에 SIGKILL —
  메모리가 모자랄 때 커널이 하는 일): 렌더러가 죽은 탭은 닫히지도 떨어지지도 않아(`isClosed()` false)
  그 봇의 탭으로 남고, Playwright는 그 탭의 `goto`를 부를 때마다 0–4ms에 거절한다(`Page crashed`).
  고치기 전: `/navigate` 502 `laf:navigation_failed`, 읽기·스냅샷·스크린샷·가리키기·클릭·키·스크롤 502
  `laf:browser_failed`(전부 0–3ms, 멈추는 것은 없다), `/tabs/switch`만 죽은 탭을 그대로 보여 주며 200 —
  봇이 계속 부르니 10분 쉼 닫기도 오지 않는다.
  - **탭을 놓는다.** 렌더러의 죽음은 두 길로 알고 한 번만 센다: 브라우저의 `crash` 이벤트(탭이 생긴
    순간부터 듣는다 — 봇의 것이 되기 전에 죽은 탭은 넘겨받지도, 빈 탭으로 내주지도 않는다), 그리고 아무도
    듣지 못한 죽음은 그 탭에서 실패한 호출(`Page crashed`·`Target crashed`)로 안다 — 그 호출은 502
    `laf:browser_failed`로 답하고 다음 호출부터 된다. 탭은 봇의 목록에서 빠지고 닫힌다(닫기는 기다리지
    않는다). warn 한 줄 `tab_crashed` — 봇, 사이트의 origin, 그 봇의 탭 수뿐이고 경로·쿼리·제목은 없다 —
    은 봇 하나에 1분에 한 줄을 넘지 않고, 쓰지 않은 것은 다음 줄의 `unsaid`에 센다.
  - **새 탭은 누가 그 봇의 탭을 달라고 할 때 열린다.** 죽은 순간에 열지는 않는다(메모리가 모자라 죽은
    자리에 렌더러를 하나 더 얹는 일이다). 봇의 다음 호출이 열고, 사람이 실시간 화면을 보고 있으면 그
    화면이 1초마다 탭을 묻기 때문에 1초 안에 열린다. 봇에게 남은 탭이 있으면 그 탭으로 돌아간다.
  - **봇이 다시 볼 때까지 아무것도 하지 않는다.** 봇이 있던 탭이 사라지면 — 렌더러가 죽었든, 사이트가
    스스로 닫았든(제 일을 마친 로그인 창) — 봇은 보지 않은 탭 위에 있게 된다. 처음 고친 판(그리고 사이트가
    닫은 탭에 대해서는 그 전의 모든 판)에서 잰 것: 로그인 팝업의 칸에 비밀값을 부탁해 둔 채 팝업이
    사라지면, 사람이 친 값이 **뒤에 있던 페이지의 같은 ref 칸**에 들어갔고(200 `supplied: true`) 기록에는
    팝업의 사이트가 남았다; ref 없는 Enter와 스크롤도 뒤의 페이지에 갔다. 지금은 그 탭에 걸려 있던 부탁(값·
    도움)이 "아무도 답하지 않음"으로 끝나고(기다리던 호출은 `laf:secret_not_entered`·
    `laf:nobody_took_control`을 듣는다 — "입력했다"가 아니다), 사람이 친 값은 409
    `laf:secret_not_pending`으로 어디에도 들어가지 않으며, 봇의 클릭·입력·키·스크롤·탭 전환·파일 올리기·
    비밀값 부탁은 봇이 스냅샷·읽기·주소 열기 가운데 하나로 다시 보기 전까지 409 `laf:stale_refs`다.
    사람의 화면이 2초마다 받는 스크린샷은 봇이 본 것으로 치지 않는다.
  - **무슨 일이 있었는지는 그 첫 보기에 한 번 실린다**: `laf:tab_replaced`(`cause`는 `crashed`·`closed`,
    사라진 페이지의 origin) — 탭에 있던 것(채우던 양식)은 없어졌고 사이트 로그인은 그대로라는 사실이다.
    그 전에는 다음 읽기가 200 `about:blank`에 빈 글로 왔고 아무 말이 없었다.
  - 페이지를 여는 도중에 죽으면 `laf:navigation_failed`(사이트 탓 — "거듭 열지 마라")가 아니라
    `laf:browser_failed`("한 번만 다시 해 보고")로 곧바로 답하고, 컴퓨터가 스스로 다시 열지는 않는다 — 다시
    여는 것은 봇의 한 번이다. 브라우저의 렌더러가 한꺼번에 다 죽어도 봇마다 자기 탭을 새로 받고, 다른
    봇의 탭과 브라우저는 그대로다.
  - **남은 것.** 그날의 원인이 정말 메모리 부족이었는지는 재현하지 못했다 — 죽은 탭이 남기는 모양이
    그날과 같다는 것까지가 잰 것이다. 가장 그럴듯한 까닭은 고치지 않았다: 봇이 계속 부르는 동안에는 그
    봇의 탭을 세지도 닫지도 않는다(`_blank` 링크를 누를 때마다 탭 하나를 넘겨받고, 탭을 닫는 경로는 없고,
    10분 쉼 닫기는 봇의 마지막 호출 시각을 본다) — 네이버 과제 57개면 `mem_limit: 3g` 아래 살아 있는
    렌더러가 수십 개다. 그리고 DevTools의 `Page.crash`(렌더러가 스스로 죽는 길)는 노트북에서는 같은
    모양을 남겼지만 CI의 Linux 러너에서는 5초 안에 아무것도 끝내지 못했다(원인 미확인) — 스스로 죽는
    렌더러가 Linux 샌드박스 안에서 어떻게 끝나는지는 재지 못했고, 끝나지 않고 멈춘다면 그것은 30초 기한이
    탭을 가는 쪽(§3)의 일이다.
- **root가 아니고, 샌드박스가 켜져 있다.** 컨테이너는 `pwuser`(1001)로 돌고, 렌더러마다
  자기 사용자·PID·네트워크 네임스페이스에 들어간다. 이것을 가능하게 하는 것이 compose의
  `security_opt`(Playwright의 seccomp 프로필) — 빠지면 브라우저가 "No usable sandbox!"로
  아예 뜨지 않는다. 실측(2026-09-13, Ubuntu 24.04 arm64): 무거운 페이지 메모리 중앙값
  312→317MiB(네이버), 343→360MiB(네이버 뉴스).
- **넘겨주기도 같은 규칙을 받는다.** 배포 안의 주소(내부 이름·사설 IP·메타데이터)로 가는
  리다이렉트·스크립트 이동·iframe·팝업은 요청이 나가기 **전에** 멈춘다(`laf:navigation_refused`).
  `computer_navigate`가 다른 호스트로 넘어가면 그 호스트도 경계 규칙이 먼저 판정한다 — 막는
  규칙이면 열지 않고, 묻는 규칙이면 그 호스트에 대해 묻는다.
- **이 앱 자신과 그 로그인 입구는 열지 않는다** (2026-10-03, `shared/net/own-addresses.ts`).
  봇의 질문에 사람이 답하는 곳이 이 앱이고, 봇의 브라우저에는 사람이 네이버·카카오·구글에
  로그인해 둔 프로파일이 있다 — 앱에 로그인하는 바로 그 계정들이다. 브라우저가 앱을 열 수 있으면
  봇이 사람으로 로그인해 자기 질문의 '허용'을 누를 수 있다. 그래서 서버는 봇이 말한 주소를,
  브라우저는 그 뒤의 모든 넘겨주기를 — 로그인 제공자가 앱의 콜백으로 되돌려 보내는 것까지 —
  요청이 나가기 **전에** 막는다(`laf:own_address_refused`). 사설 주소 옵트인보다 앞이라, 노트북의
  개발 브라우저도 자기 앱은 열지 않는다. "자기 주소"는 서버가 이미 읽는 네 변수
  (`BETTER_AUTH_URL`·`PUBLIC_ORIGIN`·`TRUSTED_ORIGINS`·`LAF_OIDC_ISSUER`)에서 읽고, compose가 같은
  표현으로 브라우저 컨테이너에도 넘긴다. 호스트와 포트로 비교한다 — 이름의 끝이나 앞을 맞추지
  않는다: 이웃 배포와 상위 도메인은 남의 사이트다.
  - 실측(2026-10-03, 진짜 Chromium, 로컬): 앱 주소를 직접, 리다이렉트로, 스크립트 이동으로,
    iframe으로 — 넷 다 멈추고 앱 쪽 서버는 요청을 하나도 받지 않았다.
  - 재지 못한 것: 함대 VM에서 봇의 브라우저가 자기 배포의 공개 주소에 실제로 닿는지(호스트
    방화벽이 이미 막고 있을 수 있다), 제공자 로그인이 사람 손 없이 끝나는지.
  - 목록에 없는 것: 함대의 입구 페이지 — 배포는 그 주소를 모른다. 거기서 시작한 로그인도
    브로커와 앱의 콜백에서 멈춘다. 공개 IP를 숫자로 친 주소도 목록에 없다(그 주소는 앱의 origin이
    아니어서 세션도 콜백도 따라오지 않는다).
  - `TRUSTED_ORIGINS`가 비어 있으면 서버는 `http://localhost:3000`(Vite 개발 서버)을 믿는다. 그
    기본값도 앱의 주소라 목록에 들어간다 — 서버와 브라우저가 같은 상수를 읽는다
    (`DEFAULT_TRUSTED_ORIGIN`).
  - 옛 compose로 뜬 컨테이너는 목록을 받지 못한다(부팅 줄 `ownAddresses`가 그 기본값
    `localhost:3000` 하나뿐). 그때는 서버의 두 검사 — 봇이 말한 주소와 도착한 주소 — 가 남는다.
  - 서버를 소스로 돌리고 브라우저만 컨테이너로 띄운 노트북에서는 두 쪽이 다른 환경을 읽는다.
    컨테이너 안의 `localhost`는 컨테이너 자신이고, 호스트의 앱은 `host.docker.internal:<포트>`로만
    닿는데 그 주소는 앱의 origin이 아니라 서버가 상태를 바꾸는 요청을 거절한다(403).
- **라벨이 바뀐 버튼은 누르지 않는다.** 스냅샷 뒤에 "저장"이 "결제하기"로 바뀌면 클릭을
  거절하고(`laf:label_changed`), 봇이 다시 보고 바뀐 이름으로 판정받는다.
- **한 응답에 여러 행동을 부르면 부른 순서대로 하고, 하나가 멈추면 그 뒤의 행동은 하지 않는다**
  (2026-10-04, `server/src/runner/round-stop.ts`). 칸 셋을 채우고 검색을 누르는 것을 한 번에 부를 수
  있다. 그 가운데 하나가 거절·대기·실패로 끝나거나, 페이지를 옮기거나(`page`가 온 클릭·Enter),
  알림창을 띄우거나(`laf:dialog`), 주소 열기·탭 바꾸기·인계·비밀값 요청이면, 같은 응답의 그 뒤
  행동(클릭·입력·키·스크롤·올리기·이동·탭·인계·비밀값)은 `laf:step_not_reached`로 답하고 컴퓨터에도
  경계에도 가지 않는다 — 감사에 `computer.action_*` 줄이 남지 않는다. 스냅샷·읽기·작업 공간 파일과
  브라우저 밖의 도구는 그 뒤에도 돈다. 고친 구멍: 루틴에서 승인을 기다리던 칸이 `laf:nobody_answered`로
  돌아와도 다음 행동이 그대로 돌아서, 비어 있는 칸 위로 검색이 눌렸다.
- **봇을 지우면 그 봇의 탭이 닫히고 로그인은 남는다** (2026-09-16에 바뀌었다). 그 로그인은 그
  봇의 것이 아니라 사람의 것이고 나머지 봇들이 쓰고 있다. 감사에 `computer.released`가 남는다.
  ~~"브라우저와 로그인이 함께 지워진다"~~ — 프로파일이 봇마다 따로였을 때의 문장이다. 실측은
  그 시절 것이다(봇 5개 × 항해 20회 → 삭제: 545→150MiB, pids 284→9, 프로필 0개). 로그인을
  정말로 지우는 문은 컴퓨터 화면의 초기화와 계정 탈퇴, 둘뿐이고 둘 다 먼저 묻는다.
- **10분 쉬면 그 봇의 탭을 닫고, 마지막 봇의 탭이 닫히면 브라우저도 닫는다.** 쿠키는 볼륨에
  남으므로 로그아웃되지 않는다.
  다시 여는 데 드는 시간 — 실측: 컨텍스트 실행 **124\~136ms**, 컨테이너에서
  `navigate`까지 포함해 **637\~776ms**(닫지 않았을 때 700ms와 사실상 같다).

## 3. 실제 사이트에서 잰 것 (2026-09-03, 로그인 없이 첫 화면만)

`computer_navigate` → `computer_read` → `computer_snapshot`을 순서대로 부른
결과다. **고치기 전 / 고친 뒤**이고, 로그인은 하지 않았다.

| 사이트 | 본문 글자 수 | 본문이 실제로 있나 | 누를 수 있는 것 |
|---|---|---|---|
| `smartstore.naver.com` (→ `sell.smartstore.naver.com/home`) | **0 → 1,403** | 아무것도 없음 → 로그인 벽이 그대로 보임(`로그인하기`·`가입하기`·`네이버 커머스 ID 알아보기`) | **0 → 41** |
| `www.naver.com` | **1,696 → 3,406** | 스킵 링크뿐(뉴스·메일·카페 없음) → 뉴스·메일·카페·쇼핑 모두 보임, iframe 6개 본문 합쳐짐 | **130 → 200**(상한에 걸려 잘림) |
| `www.hometax.go.kr` (→ WebSquare 셸) | **502 오류 → 222\~519** | 아예 못 읽음(“Execution context was destroyed”) → 로그인·인증센터·전체메뉴·근로장려금까지 읽힘. 실행마다 다르고, 부족하면 `computer_read`를 한 번 더 부르면 된다 | **0 → 16\~57** |
| `ceo.baemin.com` | **331 → 2,407** | 줄바꿈 하나 없이 메뉴만 이어붙은 331자 → 사람이 보는 화면 그대로(줄바꿈 259개) | **43 → 101** |

읽을 것: 스마트스토어의 0자는 SPA 셸을 `domcontentloaded`에서 바로 읽어서 나온
숫자이고, 배민의 331자는 `<body>`를 **복제한 뒤** `innerText`를 읽어서 나온
숫자다(분리된 노드의 `innerText`는 `textContent`와 같아서 줄바꿈이 없고 숨은
메뉴가 섞인다). 홈택스의 502는 셸이 리다이렉트하는 도중에 읽어서 났다.

한글 렌더링은 이미지에서도 정상이다(스크린샷으로 확인). 인증 화면의
`공동·금융인증`·`간편인증`·`아이디 로그인` 세 갈래가 그대로 보이며, 앞의 둘은
위 1절대로 사람 몫이다.

### 직무 실측표 (2026-09-06, 로컬 스택, `z-ai/glm-5.3-flash` via OpenRouter)

출시 계획 2-B. UI에서 만든 봇으로, 실제 서버·agent-bot·컨테이너의 브라우저를 통해 쟀다.
페이지는 `agent-computer/tests/fixtures/`의 픽스처(호스트에서 서빙,
`host.docker.internal`로 열림 — 서버에 `AGENT_COMPUTER_ALLOW_PRIVATE_HOSTS=true`
없이는 `.internal` 이름이 거절된다). 알림톡은 가짜 솔라피(임시 포트)로 — 실제 발송 없음.

같은 원인으로 멈춘 것 둘:

- 새 탭 링크로 열려 넘겨받은 탭에서 폼을 보낸 뒤의 `/navigate`: **70초 무응답 → 200 0.55초**. 탭의
  프레임 id를 문서에게 묻고(`Page.getFrameTree`) 세션 detach를 기다렸다(`mainFrameIdOf`). id는 탭마다 첫
  `/navigate`에 기억되므로, 처음 쓰는 탭만 걸렸다.
- 실시간 화면을 연 채 넘어가는 중에 `/computers/reset`: **29.3초 → 305ms**. 화면 캐스트의
  `stopScreencast`와 detach를 기다렸다(`screencast.ts`).

**어떻게 아는가.** 탭마다 CDP 세션 하나로 브라우저의 Page 이벤트를 듣는다: 문서를 바꾸는 내비게이션의
시작(`frameStartedNavigating`)과 세 끝 — 도착(`frameNavigated`, 오류 페이지 포함), 문서 없이
멈춤(`frameStoppedLoading`, 204는 시작 4ms 뒤에 왔다), 다운로드. 이 기록은 **문서가 기한 안에 답하지
않았을 때만** 읽는다 — 끝을 놓친 기록이 답하는 페이지를 "열리는 중"으로 만들 수는 없다. 탭이 열리자마자
보낸 `goto`(8/8)도, 새 탭의 스크립트가 곧바로 결제창 폼을 보낸 경우(6/6)도 시작을 들었다.

**비밀 칸.** 넘어가는 중에는 문서가 아무것도 답하지 않으므로 답에 페이지 내용이 없다(요소 0개, 본문과
제목 `""`), 알림은 가는 곳의 origin만 싣는다. 트리를 찍은 뒤 페이지가 답을 멈춰 비밀값을 친 칸을 끝까지
찾지 못하면, 넘어가는 중이면 요소 없이 답하고 아니면 그 스냅샷의 모든 입력 칸 값을 비운다. `hung-site.test.ts`가
매번 확인한다: 비밀값을 친 뒤 GET 폼으로, 또 `/navigate`로 `/hang`에 보내고 다섯 가지 보기가 모두 5초 안에
200으로 오며 응답 전체에 값이 없는지. 고치기 전 코드에서는 폼 쪽이 60초 제한에 걸리고 `/navigate` 쪽은
`/read` 502로 실패한다.

**평범한 페이지는 그대로다.** `/`·`/pw`·`/sites/smartstore-orders`에서 15번씩 두 차례, 중앙값 전→후:
읽기 3–6→2–5ms, 스냅샷 8–12→8–13ms, 스크린샷 32–35→32–39ms, 탭 전환 1→1–3ms.

**남은 것.**

- 답하지 않는 사이트로 가는 링크를 **누르는 것 자체**는 행동 기한 10초를 다 쓰고 409
  `laf:element_not_actionable`로 온다(전후 모두 10.0초) — 클릭은 이미 일어났는데. Playwright의 클릭이
  자기가 시작한 내비게이션의 도착을 기다린다. 바꾸지 않았다: 기다리지 않게 하면 클릭의 답에 실리는 주소가
  옮겨 가기 전의 것이 되고, 게이트웨이의 스냅샷 캐시가 그 주소를 따라간다(`pageMoved`) — 따로 잴 일이다.
- 답하지 않는 사이트를 **새 탭**으로 여는 링크: 그 탭은 10초가 지나도 `tabs`에 나오지 않는다.
  Playwright는 첫 문서가 도착한 탭만 넘겨준다. 봇은 원래 탭에 남고 그 탭의 보기는 평소대로 답한다.
- `/navigate`가 기한에 걸려 탭을 간 직후의 `/tabs/switch {index: 0}` 답에는 `active: true`인 탭이
  없었다(전후 모두). 닫히는 중인 옛 탭을 고른 것으로 보이며, 따로 재지 않았다.

## 5. 봇이 받는 사실 코드

전부 `shared/prompt/tool-results.ko.ts`에 한국어가 있다. 서버와 컨테이너는 코드만
보내고 문장은 거기서 붙는다. 컨테이너가 거절하거나 실패할 때는 `error`와 `code`에 **같은 코드**를
싣는다(`agent-computer/src/respond.ts` `fact`) — 영어 문장도, Playwright 메시지도 아니다. Playwright
메시지는 호출 기록을 달고 오고, `fill` 실패의 호출 기록에는 입력하던 값이 들어 있었다(2026-09-14 실측,
`/human/secret` 실패 응답에 사람이 친 비밀값). 예외는 없다: `laf:page_timeout`도 `error`에 Playwright의
첫 줄을 남기다가, 서버 클라이언트가 `code`를 읽게 된 뒤로 코드만 싣는다.

| 코드 | 언제 |
|---|---|
| `laf:dialog` | 페이지가 `alert`/`confirm`/`prompt`를 띄웠다. 내용이 함께 온다 |
| `laf:downloaded` | 파일이 `downloads/`에 저장됐다 |
| `laf:download_too_large` / `laf:download_failed` | 저장하지 못했다 |
| `laf:frame_opaque` | iframe 하나를 읽지 못했다 |
| `laf:page_loading` | 탭이 다음 페이지로 넘어가는 중이라 문서가 답하지 않았다. 가는 곳의 `origin`과 `loadingMs`가 함께 온다 |
| `laf:tab_replaced` | 봇이 보던 탭이 사라져(렌더러가 죽었거나 사이트가 닫았다) 다른 탭이나 새 빈 탭으로 옮겨졌다. 그 뒤 첫 보기에 한 번, `cause`와 사라진 페이지의 `origin`이 함께 온다 |
| `laf:secret_request_lost` | 재시작으로 비밀값 요청이 사라졌다 |
| `laf:tab_missing` | 그 번호의 탭이 없다 |
| `laf:stale_refs` | 스냅샷이 낡았다. 다시 찍어야 한다 |
| `laf:label_changed` | 스냅샷 뒤에 요소의 이름이 바뀌어서 누르지 않았다 |
| `laf:element_not_actionable` | 그 요소가 행동을 받지 않았다(가려짐·숨음·비활성, 글자나 파일을 못 넣는 요소) |
| `laf:page_timeout` | 페이지가 기한 안에 열리지 않았다. 탭이나 브라우저를 갈았다(`recycled`) |
| `laf:navigation_failed` | 그 주소를 열 수 없었다(이름 없음·연결 거절) |
| `laf:navigation_refused` | 배포 안의 주소로 넘어가려 해서 막았다 |
| `laf:own_address_refused` | 이 앱 자신이나 그 로그인 주소라서 열지 않았다 |
| `laf:browser_failed` | 브라우저가 그 동작을 끝내지 못했다 |
| `laf:request_invalid` | 요청에 필요한 값이 빠졌다. 어느 값인지 `field` |
| `laf:file_path_refused` / `laf:file_not_found` / `laf:file_wrong_kind` / `laf:file_too_large` / `laf:file_failed` | 작업 공간 파일 요청. 너무 크면 `bytes`·`limit` |
| `laf:secret_not_pending` | 기다리는 비밀값 요청이 없는데 값이 왔다 |
| `laf:bot_header_missing` | 어느 봇인지 말하지 않은 호출(배포 버그) |
| `laf:computer_token_refused` / `laf:computer_route_unknown` | 비밀이 맞지 않거나 없는 경로(배포 버그) |

## 사이트 연결 카탈로그

로그인이 필요한 국내 서비스는 `shared/sites/catalogue.ts`에 이름·로그인 주소·"연결하면 봇이 하는 일"·서명인 판정이 데이터로 있고, 앱의 "사이트 연결" 카드가 그것을 그린다. 사이트를 더하는 것은 표에 행 하나이지 마이그레이션이 아니다. 사람이 로그인을 인계한 뒤 돌려주면 봇이 화면을 읽어 연결 여부를 적고, 이후 모든 탐색이 같은 판정으로 "다시 로그인 필요"를 갱신한다(`server/src/computer/site-connections.ts`).
