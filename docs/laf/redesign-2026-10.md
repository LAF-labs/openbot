## 1. 화면

### PC (PC 앱, 그리고 덤인 브라우저)

```
┌──────────────┬───────────────────────────────────────────────┐
│ ⌂            │           [ 채팅 | 프로젝트 ]       검색  (나) │
│ ┌──────────┐ │                                               │
│ │ 위젯      │ │   채팅 또는 프로젝트의 대화                     │
│ └──────────┘ │                                               │
│ ┌──────────┐ │                                               │
│ │ 위젯      │ │                                               │
│ └──────────┘ │                                               │
│ + 새 패널    │   [ 메시지 입력                       +  🎙 ]  │
└──────────────┴───────────────────────────────────────────────┘
  홈 패널          주 화면
```

- **홈 패널은 왼쪽 옆 패널이다.** 기본 너비 20%(최소 280px), 완전히 접을 수 있고, 완전히 펼치면
  70%다. 펼쳐도 오른쪽 채팅은 최소 360px를 남긴다 — PC 앱의 최소 창이 1024px이라
  (`desktop/src-tauri/tauri.conf.json`) 70%면 채팅이 307px가 되는데, 채팅 카드는 폰 폭(약 360px)에
  맞춰 그려져 있다. 식으로는 `max(20%, 280px)`와 `min(70%, 창 − 360px)`. 고른 너비는 기기마다
  기억한다(한 사람의 편의라서 브라우저 저장소로 충분하다).
- **홈 패널 왼쪽 위의 홈 버튼**이 패널을 접고 편다.
- **주 화면은 채팅 또는 프로젝트다.** 위 가운데의 전환기 `[채팅 | 프로젝트]`가 고른다(참고 화면:
  Hark의 같은 자리). 프로젝트를 고르면 프로젝트 목록, 하나를 고르면 그 프로젝트의 대화.
- **위 오른쪽은 검색(통합검색)과 프로필 버튼이다.** 홈 패널을 접어도 둘은 남는다.
- **사이드바(`BotSidebar`)를 지운다.** 그 메뉴 — 대화·소식·아이디어·목표·만든 것, 그리고 메뉴
  아래의 수첩·루틴·스킬·연결·도움말 — 는 프로필 버튼을 누르면 뜨는 메뉴로 합친다. 새 메뉴
  "계정"이 여기 들어간다(§6).
- 권고(미정): 소식·목표·만든 것·오늘(`bot-day.tsx`)은 이미 고정된 패널처럼 동작한다. 홈 패널의
  기본 위젯 후보다.

### 모바일

- **홈 · 채팅 · 프로젝트 세 화면을 사진 넘기듯 좌우로 넘긴다. 기본은 채팅이다.**
- 구현의 표준: CSS scroll-snap 가로 페이저(`scroll-snap-type: x mandatory`). 관성과 멈춤은 웹뷰가
  처리하니 사진 앱과 같은 손맛이 나고, 손으로 짠 제스처 코드가 iOS와 싸우지 않는다. 위의
  전환기(`홈 | 채팅 | 프로젝트`)가 지금 화면의 표시이자 누르면 가는 탭이다.
- **iOS와 충돌하지 않게:**
  - 설치 앱(WKWebView)은 웹뷰의 뒤로가기 스와이프를 끈다. 가장자리 스와이프는 페이저의 것이다.
  - 모바일 브라우저(덤)에서는 가장자리 스와이프가 브라우저의 뒤로가기로 남는다. 그래서 페이저는
    화면 전환을 방문 기록에 쌓지 않는다 — 뒤로가기가 세 화면 사이를 오가지 않는다.
  - 가로로 스크롤되는 위젯(탭, 차트) 안에서 시작한 스와이프는 위젯이 먼저 받는다.
  - 키보드가 올라와 있는 동안은 넘기지 않는다.
- 하단 탭바(`PhoneTabBar`)를 지운다. 메뉴는 PC와 같이 프로필 버튼이다.
- **세 화면의 틀** (참고: Hark 폰 앱 화면 세 장, 2026-10-09 김기범이 보냄 — 사람의 이름과 메일 내용이
  보여 저장소에 올리지 않고 모양만 옮긴다):

  ```
  ┌──────────────────────────────┐   왼쪽 버튼은 화면마다 다르다:
  │ (버튼) [ 홈 | 채팅 | 프로젝트 ] (나) │     홈 → 새 패널(+), 채팅 → 검색,
  │                              │     프로젝트 → 새 프로젝트(+)
  │  화면의 내용                   │
  │                              │
  │ [ 메시지 입력          +  🎙 ] │   입력창은 홈과 채팅에 늘 있다
  └──────────────────────────────┘
  ```

  - **홈:** 위에 행동 줄 — 기다리는 일이나 봇의 제안이 한 줄에 하나, 첫 낱말이 동사 칩(답장 · 신청 ·
    확인)이고 뒤는 한 문장이다. 그 아래 패널, 맨 아래 "새 패널 만들기". 패널에는 마지막으로 갱신한
    때가 작게 붙는다("50분 전"). 홈의 입력창에 쓴 말은 메인 채팅으로 간다.
  - **채팅:** 메인 대화. 날짜 구분선이 있고, 루틴의 결과(아침 브리프)는 머리말과 함께 대화에 들어온다.
    봇이 일을 프로젝트로 모으자고 먼저 제안할 수 있고, 대화에서 만든 결과를 홈에 저장했다고 말한다.
  - **프로젝트:** 프로젝트 이름의 목록. 하나를 누르면 그 프로젝트의 대화가 열린다.

## 2. 홈 패널과 위젯 (Hark 방식)

Hark가 패널을 만들고 돌리는 방식(2026-10-08 김기범의 설명):

1. **해석.** 요청을 주제, 갱신 리듬(실시간/매일/고정), 사용 방식(보기/링크/버튼)으로 구조화한다.
2. **계획.** 필요한 값과 각 값의 출처를 정한다.
3. **수집.** 백그라운드 에이전트가 웹 검색, 페이지 읽기, 헤드리스 브라우저, 연결된 계정으로 실제
   값을 모은다.
4. **구성.** 따로 있는 작성 모델이 정해진 컴포넌트(큰 숫자, 차트, 탭, 리스트, 일정, 카운트다운
   등)를 조합해 화면 스펙을 만들고 값과 묶는다. 임의의 HTML이 아니다.
5. **검증·게시.** 스펙과 이미지 주소를 검사하고 홈에 올린다. 모으지 못한 값은 지어내지 않고
   빌드를 멈춘다.
6. **갱신.** 수집 방법(주소, 브라우저 단계)을 절차서로 저장하고, 스케줄러가 최소 1시간마다 다시
   돌려 값만 바꾼다. 로그인 만료나 출처 변경에 막히면 패널에 원인을 보인다.

Hark의 제약: 이벤트 트리거·푸시 없음(시간 기반만), 사용자 입력 저장 없음, 버튼은 채팅으로 메시지를
보내거나 웹페이지를 여는 것뿐.

**우리 쪽 결정:** 이 방식으로 만든다. 컴포넌트를 조합해 무엇이든 만들 수 있게 하되, 어휘는 닫혀
있다 — 임의 HTML 컴포넌트(`sandboxed`)는 관리자 전용으로 남는다. 출발점은 이미 있는 것이다:

- 정해진 컴포넌트 = 갤러리 카드 15종(`app/src/lib/copilot/gallery-registry.ts`,
  `components/gallery/*`), 봇별 허락은 `components`·`component_functions`·`component_exclusions`.
- 값은 모델이 아니라 출처가 채운다(`server/src/components/functions.ts` 머리말). 패널의 값마다
  그 값을 읽은 출처를 묶는다 — `feed_post`가 그 실행이 실제로 연 출처만 받는 것과 같은 규칙.
- 갱신 = 루틴(`laf_routines`, 루틴의 메모장 `routine_note`).
- 위젯 데이터의 계약 = `laf.watch`(`mcp-contract.md` §1), 화면이 없어 지웠던 것.

**구현 메모:**

- 패널은 Postgres에 둔다(스펙, 바인딩, 마지막 값, 출처, 상태). PC와 폰이 같은 홈을 본다.
- 갤러리 카드는 지금 CopilotKit 런타임(800 kB) 안에서만 그려진다. 홈에서는 렌더러만 떼어 그린다.
- 패널을 만들고 고치는 도구는 `tool_search`/`tool_call` 뒤에 둔다(목표 도구의 선례). 매 턴의 머리에
  얹지 않는다.
- 갱신은 웹 검색과 페이지 읽기를 먼저 쓰고, 브라우저는 그것으로 안 될 때만 쓴다. 패널 수와 최소
  갱신 주기에 상한을 둔다(1 OCPU / 6GB VM).

## 3. 프로젝트 (사이드 세션)

Hark의 project와 같다.

- **메인 세션은 언제나 그 메인 세션이다.** 사람은 프로젝트를 여러 개 만들 수 있다.
- **프로젝트마다 오케스트레이터가 하나 있다.** 같은 봇이고, 컨텍스트는 분리된다.
- **통합검색:** 사람이 앱에서 모든 프로젝트와 메인의 대화 내역을 검색한다. 메인 에이전트도 같은
  검색을 도구로 쓴다. 한국어는 Postgres `pg_trgm`(부분 문자열 인덱스)으로 — 기본 전문 검색에는
  한국어 형태소 분석이 없다.
- **요약은 준비만 한다.** 메인 대화에 미리 넣지 않는다. 사람이 원하거나 에이전트가 필요를 느낄 때
  도구로 읽는다. 가장 싸게: 읽을 때 만들고, 그 프로젝트의 마지막 메시지 번호로 캐시한다. 아무도
  읽지 않는 프로젝트는 비용이 0이다. 프로젝트에 매일 밤 드리밍을 돌리지 않는다.
- **메인은 프로젝트 오케스트레이터에게 물을 수 있다. 읽기 전용이다.** 질의를 받은 턴에서 프로젝트
  쪽은 브라우저나 실행 도구로 아무것도 하지 못한다 — 프로젝트의 행동은 그 프로젝트 화면에서, 사람이
  보는 데서만 일어난다. **읽기 전용은 도구를 빼서가 아니라 서버가 실행을 거절해서 지킨다.** 질의
  턴의 도구 목록은 그 프로젝트의 평소 목록 그대로다: 질의 한 번을 위해 도구를 뺐다 되돌리면 프로젝트
  대화의 머리가 두 번 바뀌어 질의와 그 다음 평소 턴이 둘 다 전체 기록을 다시 과금한다. 그대로 두면
  질의는 프로젝트의 캐시된 머리 위에 질문 하나를 얹은 값이고, 질의를 기록에 남기지 않으면(미정 5의
  권고) 다음 평소 턴의 머리도 그대로다. **질의는 그 프로젝트의 턴과 한 줄에 선다.** 엔진은 같은
  대화의 턴이 둘 돌지 않게 대화별 `live`로 막는다(`server/src/turns/engine.ts`). 질의도 그 막음을
  지나야 한다 — 차선을 브라우저 빌리기로 좁히면 둘 다 브라우저를 안 쓰니 함께 돌 수 있게 되고, 그러면
  반쯤 진행된 기록을 읽고 답한다. 그 프로젝트에 돌고 있는 턴이 있으면 질의는 끝나기를 기다리고(상한
  있음), 상한을 넘으면 "지금 그 프로젝트가 일하는 중"이라고 돌려준다. **질의는 봇 차선을 잡지 않는다.**
  질의를 부른 메인 턴이 이미 차선을 쥐고 있고(`take()`, 다시 들어갈 수 없는 잡기), 질의가 엔진의 평소
  턴 경로로 차선을 다시 잡으면 메인 턴이 질의의 답을, 질의가 메인의 차선을 서로 기다려 모든 질의가
  멈춘다 — §5의 차선 변경보다 먼저 들어가든 나중에 들어가든. 질의는 실행을 거절하므로 차선이 지키는 것
  (브라우저, 승인의 귀속)과 상관이 없다. 그래서 질의의 경로는 대화별 `live` 막음만 지나고 차선은 건너뛴다.
- 메인 에이전트의 도구는 검색·요약 읽기·질의를 하나로 묶고, **메인 대화의 처음부터 늘 있다.**
  프로젝트가 없으면 빈 결과를 돌려준다. 도구는 매 턴 과금되는 머리이고, "언제 주는가"는 대화마다
  정하지 대화 중간에 바꾸지 않는다 — 첫 프로젝트가 생길 때 나타나는 도구는 평생 쌓인 메인 대화
  전체를 다시 과금한다(`skill_view`가 첫 스킬과 함께 나타나던 것과 같은 실패).

**구현 메모:**

- 지금은 "봇 하나만 있는 가장 오래된 채널"이 곧 그 대화다(`server/src/channels/solo-channel.ts`
  `soloConversationOf`). 루틴 배달, 루틴 장부, 만든 것, 읽지 않음, 앱의 홈과 사이드바가 이 규칙을
  쓴다. 대화의 종류(메인/프로젝트)를 적는 열이 필요하다.
- 2026-09-24 이전 계정에는 봇이 여럿이고 1:1 채널도 여럿 남아 있다(봇 셋에 채널 열셋). 그 계정은
  봇을 하나도 잃지 않는다(`deployment-model.md` "봇은 하나다" 5항) — 그대로면 사이드바와 함께 유일한
  봇 전환기가 사라지고, 채널은 갑자기 프로젝트로 보인다. 그래서 마이그레이션은 봇마다 나눈다: 그
  봇의 가장 오래된 1:1 채널이 그 봇의 메인, 같은 봇의 나머지 1:1 채널은 그 봇의 프로젝트(기록 그대로).
  "내 봇들" 전환기는 그런 계정에만 프로필 메뉴로 옮겨 남고, 봇을 고르면 그 봇의 홈·메인·프로젝트가
  열린다. 봇이 하나인 사람에게는 전환기가 없다.
  - **넘어온 프로젝트의 옛 파일.** 마이그레이션은 첨부 사본을 그 프로젝트의 폴더로 옮긴다. 첨부 행에
    채널과 작업공간 경로가 있어서 어느 대화의 것인지 안다. 그 전에 만든 다운로드, 쓰기, 결과 전문은
    어느 대화의 것인지 기록이 없어 옮길 수 없다. 그래서 넘어온 프로젝트를 지워도 그 파일들은 남는다.
    이 사실을 기록하고, 넘어온 프로젝트를 지울 때 "이 프로젝트가 생기기 전 파일은 남는다"를 사실
    코드로 돌려준다(표면이 말한다). 2026-09-24 이전에 봇이 여럿이던 계정만 해당한다.
- 대화 만들기(`server/src/channels/conversations.ts`)는 지금 기존 대화를 돌려준다. 프로젝트 만들기는
  새 경로다.
- 한 봇의 상태를 대화끼리 같이 쓴다: 30분 "아니요" 기억(`server/src/computer/approvals.ts`), 반복
  카운터(`server/src/computer/repeat.ts`). 프로젝트에서 거절한 동작이 메인에서도 막힌다 — 의도인지 정한다.
- **프로젝트 삭제는 그 대화를 가리키는 것을 전부 다룬다.** 채널을 지우면 외래 키가 있는 것
  (`channel_memberships`, `channel_agents`, `channel_threads`, `laf_answer_ratings`,
  `laf_attachments`)은 함께 가지만, 대화를 글자로만 가리키는 열은 남는다. 2026-10-08 스키마를 훑어
  나온 그런 열과 처리:

  | 표 | 열 | 처리 |
  |---|---|---|
  | `laf_thread_messages` | `thread_id` | 지운다 |
  | `laf_conversation_contexts` | `thread_id` | 지운다 |
  | `laf_thread_runs` | `thread_id` | 지운다(기록의 원본은 감사다) |
  | `laf_notifications` | `channel_id` | 지운다 — 남기면 알림이 계속 뜨고 누르면 없는 대화로 간다 |
  | `computer_standing_approvals` | `thread_id` | 지우지 않고 끝낸다(`endThread`) — 경계의 기록이 그 대화가 끝났다고 말해야 한다 |
  | `agent_memories` | `evidence_thread_id`, `evidence_message_id`, `evidence_excerpt` | 기억은 봇의 것이라 남기고 근거 셋을 모두 비운다 — 발췌는 그 프로젝트에서 사람이 한 말이다 |

  `audit_events`는 지우지 않는다(append-only, 0047과 같은 원칙). **이 목록은 테스트가 지킨다:**
  스키마에서 대화나 채널을 외래 키 없이 가리키는 열을 모두 찾아, 프로젝트 삭제의 목록에 없는 열이
  있으면 실패한다. 새 표가 대화를 가리키면서 삭제를 잊는 것을 리뷰가 하나씩 찾게 두지 않는다. 그
  테스트는 대화의 내용을 옮겨 담은 열(위의 `evidence_excerpt`처럼 대화를 가리키지는 않는 발췌)은 보지
  못한다 — 그런 열은 가리키는 열과 같은 행에 있으므로, 목록의 각 행은 열 하나가 아니라 그 행에서 그
  대화에서 온 것 전부를 처리한다.
- **메인에 옮겨진 프로젝트 내용.** 메인의 프로젝트 도구(검색, 요약, 질의)가 돌려준 결과는 메인 대화의
  도구 결과로 저장된다(`server/src/turns/engine.ts` `appendMessages`). 그래서 프로젝트를 지워도 그 사본이
  메인 대화와 그 뒤의 모든 요청에 남는다. 도구 결과에 프로젝트를 적어 두고, 프로젝트를 지울 때 그
  결과의 본문을 정해진 문구("지운 프로젝트의 내용")로 바꾼다. 호출과 결과의 짝은 그대로 두므로 공급자가
  받는 기록은 여전히 맞다. 메인 대화의 머리가 바뀌어 다음 한 턴이 기록 전체를 정가로 다시 읽지만,
  삭제는 드문 일이라 감수한다. 봇이 그 내용을 읽고 메인에 자기 말로 쓴 답과, 그 답을 줄인 요약은 남는다
  — 메인 대화 자체의 기록이기 때문이다. 이 한계도 기록에 둔다.
- **지우기 전에 그 프로젝트에서 도는 일을 멈추고, 멈춘 것을 기다린다.** 줄 서 있거나 돌고 있는
  턴이 있으면 행을 지운 뒤에도 엔진(`server/src/turns/engine.ts`)이 메시지를 덧붙여, 지운 프로젝트에
  주인 없는 기록이 새로 생긴다. 계정 삭제가 바로 이 경합 때문에 하는 일과 같다
  (`server/src/account/deletion.ts` `stopWorkFor`). 그 프로젝트의 백그라운드 일과 질의도 같다.
  **멈추기 전에 먼저 "지우는 중"으로 표시한다.** 멈추고 기다린 뒤 지우기 직전까지 틈이 있다 — 대화별
  `live`가 비는 순간 다른 탭의 메시지가 `turns/routes.ts`를 지나 `engine.send`로 들어가 실행과 메시지
  행을 만들고, 지우기가 그것을 지운 뒤에도 그 턴이 기록을 덧붙인다. 그래서 순서는 표시 → 멈추고 기다림 →
  지우기다. 표시는 Postgres에 둔다: 지우는 도중에 서버가 다시 떠도 표시가 남아 새 쓰기를 막고, 부팅이
  남은 지우기를 마저 한다.
  **표시는 그 대화에 쓰는 모든 길이 확인한다. 턴만이 아니다.** 대화와 채널 아래의 쓰기 라우트는 턴 보내기·
  멈추기(`server/src/turns/routes.ts`), 첨부 올리기(`server/src/attachments/routes.ts`), 그림 저장
  (`server/src/channels/transcript-routes.ts`), 답 평가(`server/src/support/rating-routes.ts`), 읽음·활동
  (`server/src/channels/roster-routes.ts`)이고, 여기에 질의와 백그라운드 일이 더해진다. 첨부는 특히 위험하다
  — 변환에 시간이 걸리고, 작업공간에 사본을 먼저 쓴 뒤 행을 넣는다. 지우는 중에 시작한 업로드는
  폴더를 지운 뒤에 파일을 다시 만들고, 행 넣기는 외래 키로 실패해 아무도 모르는 파일이 남는다. 그래서:
  - 표시가 있으면 이 길들은 모두 사실 코드로 거절한다(표면이 말한다). 확인은 한 곳(대화 범위 쓰기의 공통
    관문)에 두고, 테스트가 대화·채널 아래의 쓰기 라우트를 모두 찾아 각각 거절하는지 확인한다 — 새 라우트가
    확인을 빠뜨리면 실패한다.
  - "멈추고 기다림"은 턴만이 아니라 이미 시작한 업로드와, 그 프로젝트를 읽는 메인의 도구 호출 셋(검색,
    요약, 질의) 모두를 그 결과가 메인 대화에 저장될 때까지 기다린다. 표시가 선 뒤에는 셋 모두 거절한다.
    그래야 지우면서 가린 메인의 사본 위에, 진행 중이던 검색이나 요약이 새 사본을 덧붙이지 않는다.
    폴더와 행은 그 뒤에 지운다.
- **프로젝트가 만든 파일은 프로젝트의 폴더에 두고, 지울 때 폴더째 지운다.** 봇의 작업공간은 하나이고
  (`agent-computer/src/workspace.ts`), 쌓인 파일은 뒤의 어느 대화에서나 목록을 보고 읽을 수 있다.
  프로젝트가 파일을 남기는 길은 여럿이다: 첨부의 읽을 수 있는 사본(`server/src/attachments/files.ts`
  `workspacePathFor`, `uploads/…`), 브라우저 다운로드, `computer_write_file`, 길어서 잘린 도구 결과의
  전문(`server/src/computer/spillover.ts`, `.results/`). 길을 하나씩 세면 또 하나를 빠뜨린다(리뷰가 실제로
  넷째를 찾았다). 그래서 규칙을 길이 아니라 작업공간에 둔다: **프로젝트에서 도는 일의 작업공간 쓰기는
  쓰는 쪽이 누구든 그 프로젝트의 폴더(`projects/<id>/…`)를 뿌리로 갖는다.** 쓰기의 경로를 정하는 한
  곳에서 실행의 프로젝트를 보고 뿌리를 바꾸므로, 나중에 생기는 쓰기도 저절로 따른다. 테스트는 프로젝트
  턴에서 쓰기를 하는 모든 도구를 돌리고, 그 폴더 밖에 새 파일이 하나도 없음을 확인한다. 프로젝트 삭제는
  그 폴더를 통째로 지우되, 결과 전문처럼 뒤늦게 쓰이는 비동기 쓰기가 끝나기를 먼저 기다린다("멈추고
  기다림"에 포함). 계정 삭제는 작업공간을 통째로 지우므로 따로 할 일이 없다.
- **읽기도 같은 자리에서 막는다.** 읽기가 작업공간 전체에서 되면, 프로젝트 B의 턴이 `projects/A/…`를
  읽어 그 내용이 B의 도구 결과로 B의 기록에 남는다. A를 지워도 폴더와 메인의 표시된 사본만 사라지고 B의
  사본은 남는다. 그래서 경로를 정하는 같은 한 곳이 읽기도 거른다.
  - 프로젝트의 일은 자기 폴더와 `projects/` 밖의 파일만 읽는다. 다른 프로젝트의 폴더는 읽을 수도, 목록에
    보일 수도, 브라우저에 올릴 수도 없다.
  - 메인의 일은 `projects/` 아래를 직접 읽지 않는다. 메인이 프로젝트의 내용을 가져오는 길은 프로젝트
    도구 하나이고, 그 결과에는 프로젝트가 적혀 있어 지울 때 가려진다(위).
  - 테스트는 프로젝트 B의 턴과 메인 턴에서 파일을 읽는 모든 도구(읽기, 목록, 브라우저 올리기)로 A의
    파일에 닿아 보고, 모두 거절됨을 확인한다.

## 4. 메인 = 오케스트레이터

- **메인 대화는 모델과 effort를 고정한다.** 메시지마다 모델을 바꾸지 않는다 — 평생 하나의 대화인
  메인의 프롬프트 캐시가 깨진다(Muse Spark에서 캐시 적중은 50배 싸다; 턴마다 effort만 바꾸는 것도
  재 보고 기각했다, `eval-pack.md`).
- **특정 작업만 백그라운드 서브에이전트에게 넘긴다:** 브라우징, 깊은 추론, 백그라운드 일(패널
  갱신), 캡챠(§7). 서브에이전트는 자기 대화를 가지므로 다른 모델을 써도 메인 캐시를 건드리지
  않는다.
- 브라우징을 넘기면 메인의 머리에서 컴퓨터 도구 14개가 빠지고 위임 도구 하나가 남는다. 메인의
  턴이 싸진다.
- **이미 쌓인 메인 대화에는 한 번에 바꾼다.** "도구는 대화의 처음부터"는 이미 있는 대화에 거꾸로
  적용되지 않는다. 바뀐 도구 목록은 업그레이드 뒤 첫 턴에 기존 장치(`tools_changed` epoch,
  `server/src/context/conversations.ts`)로 새 epoch을 열고, 그 한 턴이 기록 전체를 정가로 낸다 — 턴마다가
  아니라 대화마다 한 번이다. 그래서 메인의 머리를 바꾸는 것(컴퓨터 도구를 빼기, 위임 도구, 프로젝트
  도구, effort 끄기, 프롬프트의 "얼굴")은 한 릴리스에 모아 한 번만 낸다.
- **대화에서 맡긴 서브에이전트는 사람을 부를 수 있다** — 승인, 비밀번호 카드, 카드 선택이 그대로
  사람에게 뜬다. 패널 갱신 같은 백그라운드 일은 루틴처럼 사람 없이 돈다(그래서 사람을 부르는
  도구가 없다, `routines.md`).

**구현 메모:**

- 지금 agent-bot의 모델은 프로세스에 하나다(`BOT_MODEL`). 서브에이전트의 역할별 모델이 필요하다.
- `eval:model`은 모델 하나를 검증한다. 위임 구조를 재는 eval과, 역할마다 모델 교체의 의식이
  필요하다.
- 비용: 일일 예산은 모델과 상관없이 토큰을 더한다(`server/src/usage/daily-budget.ts`) — 모델을 섞으면 비용으로
  센다. `laf_thread_runs`에 모델 열이 없고, `askModel`은 `costUsd`를 남기지 않는다.

## 5. 봇의 브라우저

- **가능하면 브라우저를 여러 대 띄운다.** 메인 브라우저 하나(로그인 프로필, 실시간 화면, PC에서의
  직접 조작)와 백그라운드 브라우저 풀.
- **헤드리스여도 되는 곳은 무조건 헤드리스다.** 단 정식 Chromium의 새 헤드리스 모드여야 한다. 지금은
  Playwright의 헤드리스 셸이고, 사이트가 그것을 알아본다 — 2026-10-04 측정에서 G마켓·쿠팡 403,
  11번가 빈 페이지. user agent는 고쳤지만 `Sec-Ch-Ua`는 아직 `HeadlessChrome`을 말한다
  (`agent-computer/src/browser-identity.ts`).
- **봇 차선은 브라우저를 빌리는 것으로 바꾼다.** 지금은 봇 단위로 한 줄이라(`server/src/runner/bot-lane.ts`)
  프로젝트가 브라우징하는 동안 메인 채팅도 기다린다. 브라우저를 쓰지 않는 대화는 줄을 서지 않는다.

**구현 메모:**

- 브라우저 컨테이너는 합쳐서 3GB가 상한이다(`docker-compose.yml`, 1 OCPU / 6GB + 스왑 4GB). 동시
  대수는 재고 정한다.
- 로그인이 든 프로필 폴더는 동시에 한 브라우저만 쓴다. 백그라운드 브라우저는 저장된 계정(§6)으로
  스스로 로그인한다.
- 봇 ID 헤더, 스냅샷 캐시, 승인이 가리키는 요소, 탭 상한, 실시간 화면이 모두 "봇 = 컴퓨터 하나"를
  가정한다. "봇 + 브라우저" 단위로 바꾸는 큰 일이다.
- **차선을 좁히기 전에 승인에 실행의 신원을 붙인다.** 실행 장부(`server/src/runner/run-ledger.ts`)는
  한 턴의 승인을 "같은 봇, 그 턴이 시작된 뒤"로 찾고, 그것이 그 턴의 것이라는 근거가 봇 차선이다.
  브라우저를 쓰지 않는 메인과 프로젝트의 턴이 동시에 돌면 서로의 승인 요청과 허락을 세고, 한쪽에서
  열려 있는 승인이 끝난 다른 턴을 "주인을 기다림"으로 분류한다. 승인 이벤트와 장부의 조회에
  실행(또는 대화)의 신원을 넣은 뒤에 차선을 좁힌다. 그 전까지는 브라우저를 쓰지 않는 일의 차선을 따로
  둔다.

## 6. 계정 (로그인 정보와 카드)

설정의 새 메뉴 "계정".

**로그인 정보**

- 지원하는 서비스를 고르거나 주소를 직접 넣고, 아이디와 비밀번호를 저장한다. 에이전트는 그 값으로
  로그인한다. 모델은 값을 보지 않는다 — 모델은 어느 계정인지만 고르고, 값은 서버가 꺼내 봇의
  브라우저에 넣는다.
- 사이트 연결(배민, 스마트스토어 등)의 로그인도 직접 조작 대신 이것과 비밀번호 카드로 한다.
- **사람 없이 도는 실행(루틴, 패널 갱신)도 저장된 계정으로 로그인한다.** 인증번호를 요구하면 멈추고
  이유를 패널에 보인다.
- **저장한 출처(origin)에서만, HTTPS에서만 채운다.** 봇이 페이지의 지시에 속아 비밀번호를 다른
  사이트에 넣는 것을 막는 장치다(비밀번호 관리자가 도메인을 맞추는 이유와 같다). 호스트만 보면
  `https://shop.example`에 저장한 값이 `http://shop.example`에도 맞는다 — 가로챈 HTTP 이동이 평문
  비밀번호를 받는다. 그래서 저장할 때 출처(스킴·호스트·포트)를 정규화해 두고 HTTPS만 받으며, 채울
  때는 서버가 그 입력칸이 들어 있는 프레임의 출처를 저장한 출처와 비교한다(최상위 페이지가 아니라
  프레임 — 로그인 칸이 다른 출처의 iframe 안에 있을 수 있다). 로그인 칸이 다른 하위 도메인에 있는
  사이트(예: 네이버의 `nid.naver.com`)는 저장할 때 그 출처를 함께 묶는다. 카드 값도 HTTPS 프레임에만
  넣는다.
- 채우기는 게이트웨이를 거친다: 판단과 감사(계정, 사이트, 칸 — 값은 없이). 새 의도(intent)이고
  `type`이 아니다(`type`이면 `SECRET_FIELD_RULE`이 거절한다). 지금의 비밀번호 카드
  (`server/src/computer/gateway/secrets.ts` `supplySecret`)도 `govern`을 건너뛰고 판단한 칸에 묶이지 않는다 — 같이
  고친다.
- 비밀번호 카드는 여러 칸을 받는다(지금은 하나, `computer_request_secret`).

**카드 — 우리 서버에는 두지 않고, 사람의 기기에만 둔다** (2026-10-09 김기범)

> CVC를 빼도 카드 정보를 서버에 저장하면 개인정보 보호법과 여신전문금융업법상 형사처벌 대상이 된다는
> 판단으로, 10월 8일의 "자체 암호화 DB" 결정을 바꿨다. 카드번호, 유효기간, CVC는 그 사람의 기기에만
> 저장한다. 서버의 DB, 로그, 감사, 대화 기록, 백업 어디에도 카드 정보는 없다. 카드 목록(별칭, 끝
> 4자리)도 기기에 있다.

- **어디에 두나.**
  - PC 앱: OS의 보안 저장소(macOS 키체인, Windows 자격 증명 관리자). 꺼낼 때마다 OS의 본인 확인
    (Touch ID, Windows Hello)을 거친다.
  - 모바일 앱: iOS 키체인, 안드로이드 키스토어와 생체 인증.
  - 브라우저(덤): 저장하지 않는다. 결제할 때마다 카드 카드에 직접 입력한다.
  - 여러 기기 사이에 동기화하지 않는다. 동기화하려면 서버를 거쳐야 하기 때문이다. 기기마다 따로
    등록한다. 로그아웃하면 그 기기의 카드를 지운다.
  - **앱을 지워도 카드가 남지 않게.** OS 보안 저장소는 앱을 지워도 남을 수 있다. iOS 키체인 항목은 앱을
    지운 뒤에도 남고, 같은 서명으로 다시 설치하면 다시 열린다(Apple이 설명하는 정상 동작). 그래서 카드는
    앱 자신의 데이터 폴더에 둔 무작위 키로 한 번 더 암호화해 저장소에 넣는다. 앱을 지우면 그 폴더와 키가
    사라지고, 저장소에 남은 항목은 풀 수 없는 덩어리가 된다. 다시 설치한 앱은 첫 실행에서 맞는 키가
    없는 항목을 지운다. 안드로이드 키스토어의 키는 앱과 함께 지워진다. PC에서는 앱을 휴지통에 버려도
    데이터 폴더가 남는 경우가 많으므로, 확실한 방법은 로그아웃이나 계정 메뉴의 "이 기기에서 카드 지우기"
    이다. 화면도 그렇게 말한다.
- **결제 흐름.**
  1. 봇이 결제 단계에 이르면 카드를 요청한다.
  2. 사람의 기기에 카드 선택 카드가 뜬다. 목록은 그 기기의 저장소에서 읽은 별칭과 끝 4자리다.
  3. 사람이 카드를 고르고 OS 본인 확인을 한다. 기기에 카드가 없으면 같은 카드에서 직접 입력한다.
  4. 셸이 값을 꺼내 그 결제의 채우기 표와 함께 서버에 직접 보낸다(TLS). 값은 페이지 스크립트를 거치지
     않는다(아래 "셸의 예외").
  5. 서버는 저장하지 않고 메모리에서 곧바로 agent-computer로 넘긴다. agent-computer가 채우고 버린다.
  - 사람 없이 도는 실행에서 결제할 수 없는 것이 규칙이 아니라 구조가 된다. 기기 앞에 사람이 있어야
    값이 나온다.
- **지나가는 것과 저장하는 것은 다르다.** 값은 결제하는 순간 서버와 봇의 브라우저를 지나간다(메모리).
  그 값은 어디에도 남기지 않는다. 테스트로 지킨다: 결제를 한 번 돌린 뒤 DB 전체, 로그, 감사, 대화
  기록을 직렬화하고 카드번호와 CVC가 어디에도 없음을 확인한다(사람이 친 값의 규칙과 같은 방식).
- **셸의 예외.** CLAUDE.md는 `desktop/`에 제품 로직을 두지 않는다고 한다. 카드를 기기에 두려면 셸에 OS
  보안 저장소를 여닫는 작은 다리가 필요하다(넣기, 꺼내기, 지우기, 꺼낼 때 OS 본인 확인). 다리는 카드
  저장소 하나만 다루고, 다른 제품 로직은 두지 않는다. 이 예외는 그 PR이 들어갈 때 CLAUDE.md에 적는다.
  - 셸은 원격 출처의 페이지를 띄우므로, 페이지에 끼어든 스크립트도 다리를 부를 수 있다. OS 본인 확인은
    사람이 누구인지만 확인할 뿐, 꺼낸 값을 부른 스크립트에게서 지켜 주지 않는다. 그래서 **다리는 카드
    값을 페이지에 돌려주지 않는다.** 꺼내기는 "이 표로 이 카드를 보내라"이지 "값을 달라"가 아니다.
    - 서버가 결제 요청마다 한 번만 쓰는 채우기 표를 발급한다. 표는 그 실행, 그 단계, 그 출처에 묶인
      무작위 값이다. 페이지는 표와 고른 카드의 별칭만 셸에 넘긴다.
    - 셸은 표로 서버에서 요청 내용(출처, 알면 금액)을 직접 받아 OS 본인 확인 창에 적는다. 보낼 카드의
      별칭과 끝 4자리도 셸이 자기 저장소에서 읽어 같은 창에 적는다. 페이지가 준 글은 그 창에 쓰지 않는다.
      끼어든 스크립트는 그럴듯한 확인 창을 꾸밀 수 없고, 사람이 고른 카드를 몰래 다른 카드로 바꾸면 그
      바뀐 카드가 확인 창에 보인다.
    - OS 창이 그 글을 보여 주지 않는 곳(iOS의 Face ID)에서는 셸이 본인 확인 바로 앞에 자기 확인 화면을
      띄워 같은 내용을 보여 준다.
    - 본인 확인이 끝나면 셸이 저장소에서 값을 꺼내 표와 함께 서버로 직접 보낸다. 서버는 표가 아직 쓰이지
      않았고 기다리는 요청과 맞을 때만 받는다. 페이지에는 채웠는지 실패했는지만 돌아간다.
    - 이것이 막지 못하는 것: 배포 자체가 뚫리면 서버는 어차피 값을 agent-computer로 넘기는 자리라서, 그
      순간 사람이 승인한 카드 하나를 볼 수 있다. 저장소 전체는 아니다. 카드마다, 결제마다 본인 확인을
      거친다.
- **카드에 대한 서버 쪽 보호는 값 없이 한다.**
  - 실행 동안의 기억(agent-computer), 값을 넣은 탭 닫기, 그림 끄기는 로그인과 같다(아래).
  - 실행이 끝난 뒤 서버의 대조는 카드 값을 모르므로, Luhn 검사를 통과하는 13–19자리 숫자열을 모두
    가린다. 주문번호 일부가 함께 가려질 수 있는 비용을 감수한다.
    - 카드번호의 국제 표준(ISO/IEC 7812)은 10–19자리를 허용한다. 하지만 10–12자리까지 늘 가리면
      사업자등록번호(10자리)와 휴대폰 번호(11자리)의 열에 하나가 Luhn을 통과해 가려진다 — 사장님의 봇이
      가장 많이 다루는 숫자다. 그래서 서버는 채우기를 지나 보낼 때 그 카드번호의 **길이만** 사람마다
      기억하고(숫자는 아니다), 13자리보다 짧은 카드를 넣은 사람에게만 그 길이의 숫자열을 더 가린다.
  - 카드 값을 받은 출처는 서버가 기억한다. 출처만이고 카드 정보가 아니다. **이 기억은 지우지 않는다.**
    사람이 지울 수 있게 하면, 지운 뒤 그 출처를 다시 찾을 때 사이트 쪽에 남은 카드(사이트가 자기 서버에
    둔 것)가 글이나 칸의 신호 없이 그림으로 그려질 때 막을 것이 없다. 브라우저 쪽을 비워도 사이트 쪽은
    그대로다. 계정 메뉴는 이 목록을 보여 주기만 하고, 목록은 계정과 함께 지워진다. 카드 출처는 대개
    결제창만 띄우는 출처라, 그 그림이 계속 꺼져 있어도 봇의 일에 드는 비용은 작다.
    이 기억은 사람마다 Postgres에 둔다. 브라우저 프로필과 사이트 쪽 상태는 재시작과 업그레이드를 넘어
    남으므로, 그림을 막는 이 기억도 함께 남아야 한다. 서버는 이 표를 읽어 그림을 받을지 정하고, 표를
    읽을 수 없으면 그 단계의 그림을 받지 않는다.
- **CVC도 기기에 저장한다.** 10월 8일의 "CVC 저장" 결정을 기기로 옮긴 것이다.
- 스냅샷은 이미 카드번호 칸(`autocomplete=cc-number`)을 가린다(`agent-computer/src/secret-fields.ts`).
  카드 값도 `computer_type`이 아니라 비밀 경로로만 넣는다 — `computer_type`의 인자는 대화 기록에
  그대로 남는다.
- **채운 값이 화면 그림으로 새지 않게 한다.** 스냅샷의 가림은 텍스트에만 닿는다. 단계마다 남기는
  마지막 화면(`app/src/lib/computer/last-frame.ts`)은 사람에게 비밀번호를 묻는 동안(`secretWanted`)만
  찍지 않고, 찍은 그림은 `laf_thread_messages.frame`(`server/src/channels/frames.ts`)과 백업에 남는다.
  결제 페이지는 카드번호를 그대로 보여 주는 경우가 많다 — 그대로면 서버에 두지 않기로 한 카드
  정보가 그림으로 서버에 남는다. **저장한 값(보관함의 로그인, 기기의 카드)을 채운 뒤 그 실행이 끝날 때까지는 그림을 찍지 않는다.** 칸만 가리고
  찍는 것으로는 부족하다 — 페이지가 그 값을 다른 자리에 옮겨 적을 수 있다(아래). 로그인 정보도 같다.
- **채운 값은 브라우저에서 나가는 모든 것에서 지운다.** 입력칸의 가림과 그림 끄기는 두 길만 막는다.
  허락한 출처의 페이지도 채운 값을 보이는 글로 옮길 수 있다 — 확인 화면이 카드번호를 다시 보여 주거나,
  페이지의 스크립트가 비밀번호를 본문에 쓰거나. 그러면 `computer_read`(`readSettledPageText`, 본문 글
  그대로)가 그 값을 모델에 주고, 도구 결과로 대화 기록에 남는다. 그래서 값을 넣는 쪽(agent-computer)이
  넣은 값을 기억해 두고, 나가는 모든 글 — 스냅샷, 읽은 글, 페이지 사실 — 에서 그 값을 찾아 가린 뒤
  내보낸다. 카드번호는 띄어쓰기와 하이픈을 넣은 꼴도 찾고, 끝 4자리는 남긴다.
  - **기억은 페이지가 아니라 실행에 붙는다.** 로그인과 결제는 제출하면서 다음 페이지로 가고, 값을 다시
    보여 주는 확인 화면이 바로 그 다음 페이지다 — 페이지를 떠날 때 기억을 버리면 정확히 그 화면에서
    샌다. 그래서 기억은 그 실행이 끝날 때까지, 그 실행의 모든 탭에 걸쳐 남는다.
  - **값을 넣은 탭은 그 실행이 끝날 때 닫는다.** 탭은 실행이 끝나도 10분 동안 남는다
    (`agent-computer/src/tabs.ts` `IDLE_CLOSE_MS`). 그 사이 다음 턴이 같은 탭으로 돌아오면, 기억은 이미
    버려지고 그림도 다시 찍히는데 페이지에는 비밀번호, CVC, 유효기간이 그대로 있다. 그래서 저장한 값을
    받은 탭은 10분 규칙의 예외로, 실행이 끝나는 순간 닫는다. 기억과 그림 끄기는 그 탭들이 닫힐 때까지
    유지한다. 탭을 닫으면 그 탭의 DOM과 세션 저장소도 함께 사라진다.
    - **카드 값이면 값을 받은 탭 하나로는 부족하다.** 같은 출처의 다른 탭은 `BroadcastChannel`, 공유
      워커로 CVC를 건네받아 메모리에 쥐고 있을 수 있고, 결제 팝업은 자기를 연 탭에 `postMessage`로 넘길
      수 있다. 그 탭의 메모리는 값을 받은 탭을 닫아도, 저장소를 비워도 남는다. 그래서 카드 값을 넣은
      실행이 끝나면 그 브라우저에서 다음 탭을 모두 닫는다: 값을 받은 탭, 카드 값을 받은 출처의 페이지나
      프레임을 가진 탭, 값을 받은 탭과 서로 열고 열린 탭(결제 팝업과 그 팝업을 연 탭). 그 출처의 페이지가
      모두 닫히면 전용 워커와 공유 워커도 끝나고, 서비스 워커는 아래의 저장소 비우기가 등록을 지운다.
      봇이 그 사이트에서 열어 둔 다른 탭도 닫히지만, 결제는 대개 일의 끝이라 감수한다.
  - **실행이 끝난 뒤에는 서버가 한 번 더 거른다.** 탭을 닫아도 그 출처의 localStorage와 IndexedDB는 브라우저
    프로필에 남는다(`agent-computer/src/profiles.ts`). 그래서 뒤의 실행에서 같은 출처의 페이지가 저장해 둔
    값을 다시 보여 줄 수 있다. 서버는 자기가 중계하는 모든 브라우저 글 출력을 거른다. 비밀번호는 그
    사람의 보관함 값과 대조해 가리고, 카드번호는 서버가 값을 모르므로 꼴로 가린다(위 "카드"). 걸린
    단계는 그림도 남기지 않는다. 앱이 그 단계의 그림을 올려도(`PUT /:channelId/frames/:toolCallId`) 서버가
    받지 않는다 — 글에 값이 있던 페이지라면 그림에도 있기 때문이다.
  - **그림은 글과 따로 막는다.** 글에서 값이 안 보여도 그림에는 보일 수 있다. 비밀 입력칸의 값은
    스냅샷 글에서 지워지는데(`agent-computer/src/secret-fields.ts`), 그림은 화면 그대로 찍힌다
    (`app/src/lib/computer/last-frame.ts`). 그래서 서버는 글 대조와 별개로 두 경우에 그림을 받지 않는다.
    - 그 단계의 페이지에 값이 든 비밀 입력칸이 있을 때. 대상은 비밀번호, 카드번호, CVC, 유효기간,
      인증번호 칸이다. agent-computer가 칸이 차 있다는 사실만 결과에 실어 보내고, 값은 보내지 않는다.
    - 카드 값을 받은 적이 있는 출처의 페이지일 때. 출처만 기억하고(카드 정보가 아니다), 계정이 있는 동안
      유지한다(위). CVC와 유효기간은 실행이 끝난 뒤 서버가 글로 대조하지 못하므로(아래), 그 출처의
      그림을 통째로 막는다. 캔버스에 그린 카드번호처럼 글로도 칸으로도 잡히지 않는 경우도 함께 막힌다.
    - 로그인 값에는 이 출처 기억을 두지 않는다. 카드와 무엇이 다른지:
      - 비밀번호는 칸에서 점으로 그려지고, 칸이 차 있으면 위의 규칙이 막는다.
      - 페이지가 비밀번호를 저장해 두었다가 뒤의 실행에서 보이는 글로 다시 쓰면, 서버가 보관함 값과
        대조해 그 단계의 그림까지 받지 않는다(위). 서버가 값을 알기 때문에 이 대조는 실행이 끝난 뒤에도,
        어느 실행에서든 걸린다. 카드의 CVC와 유효기간에는 이것이 없다.
      - 남는 것은 페이지가 비밀번호를 글 없이 캔버스에만 그리는 경우다. 그러려면 그 출처의 스크립트가
        비밀번호를 손에 쥐고 있어야 하고, 그런 스크립트는 그림을 끄든 말든 값을 바깥으로 보낼 수 있다.
        그림 끄기가 더 막는 것은 그 그림이 우리 대화 기록에 남는 것 하나다.
      - 그 하나를 위해 로그인 출처의 그림을 통째로 끄면, 봇이 가장 오래 일하는 곳(스마트스토어, 배민
        사장님 등)에서 "봇의 브라우저" 카드가 빈칸이 된다. 그래서 두지 않는다.
  - **CVC와 유효기간은 글 대조 대신 출처의 브라우저 상태를 되돌려 막는다.** 세 자리 숫자나 "12/27"을 모든 출력에서
    찾아 가리면 평범한 숫자와 날짜가 다 지워진다. 그래서 이 둘은 실행 동안의 기억(입력칸을 아는
    agent-computer)이 지키고, 실행이 끝난 뒤의 서버 대조에서는 뺀다. 대신 **카드 값을 넣은 실행이 끝날
    때, 카드 값을 받은 모든 출처(프레임의 출처)의 브라우저 쪽 상태를 값을 넣기 전으로 돌린다.**
    - 쿠키를 뺀 그 출처의 브라우저 데이터를 모두 비운다. 종류를 하나씩 세지 않고 "쿠키 말고 전부"로
      정한다 — Chromium의 출처 단위 지우기(CDP `Storage.clearDataForOrigin`의 `all`에서 쿠키만 뺀 것)다.
      localStorage, IndexedDB, Cache Storage, 서비스 워커, 출처 전용 파일 시스템(OPFS), 저장소 버킷이
      모두 여기에 든다. 셀 때마다 하나를 빠뜨렸다(리뷰가 OPFS를 찾았다).
    - 프레임으로 들어온 출처의 저장소는 브라우저가 최상위 사이트별로 나눠 둔다(저장소 분할). 그래서 그
      출처가 들어간 최상위 사이트마다의 칸을 모두 지운다(저장소 키 단위). 쿠키의 되돌리기(아래)도 분할된
      쿠키를 포함한다.
    - 쿠키는 비우지 않고 되돌린다. 그 출처에 처음 카드 값을 넣기 직전에 agent-computer가 그 출처의 쿠키를
      찍어 두고, 실행이 끝날 때 그 상태로 돌린다. 그 뒤에 생긴 쿠키는 지우고, 바뀐 쿠키는 되돌리고,
      사라진 쿠키는 되살린다. 결제 전에 한 로그인은 남고, 페이지가 결제하면서 쿠키에 적은 CVC나
      유효기간은 남지 않는다. 결제 뒤에 갱신된 로그인 쿠키도 되돌아가므로 그 사이트에 다시 로그인해야 할
      수 있다. 보관함에 로그인이 있으면 봇이 다시 한다.
    - 되돌릴 일(출처 목록과 찍어 둔 쿠키)은 첫 카드 값을 넣기 직전에 브라우저 프로필 옆 디스크에 적는다.
      찍어 둔 쿠키는 프로필에 이미 있는 것과 같은 것이다. agent-computer가 실행 도중에 죽었다가 다시
      뜨면, 남은 일을 다른 무엇보다 먼저 하고 지운다.
    - 그러면 사이트가 — 카드 규칙을 어기는 사이트든, 끼어든 스크립트든 — 브라우저에 담아 둔 CVC를 나중의
      실행에서 되살릴 길이 없다. 그런 출처의 그림은 위의 출처 기억이 막는다. 사이트가 자기 서버에 둔
      카드를 나중에 보여 주는 화면(가린 번호, 유효기간)은 그 사이트의 화면이다. 카드 규칙상 CVC는 그
      화면에 나오지 않는다. (2026-10-09 고침: 앞의 판에는 "CVC를 저장하지 않으면 이 틈이 사라진다"고
      잘못 적었다.)
  - **테스트가 지킨다.** 글로 나가는 출력마다 넣은 값을 심고, 나가는 바이트에 그 값이 없음을 확인한다
    (사람이 친 값의 규칙과 같다). 그림은 그렇게 확인할 수 없다 — 글자가 픽셀이 되고 압축되면 바이트에
    값이 남지 않아도 화면에는 보인다. 그래서 그림은 기억이 있는 실행에서 그림이 하나도 찍히지 않았음을
    확인한다.
    - 셸의 다리에는 카드 값을 페이지로 돌려주는 명령이 없다. 채우기 표는 두 번 쓰이지 않는다. 확인 창의
      카드는 페이지가 넘긴 별칭이 아니라 셸의 저장소에서 읽은 것이다.
    - 결제하면서 CVC를 `BroadcastChannel`로 같은 출처의 다른 탭에 넘기는 시험 페이지로 결제를 한 번
      돌리고, 실행이 끝난 뒤 그 출처의 탭이 하나도 남지 않았음을 확인한다.
    - 결제하면서 쿠키, localStorage, IndexedDB, OPFS에 CVC를 적는 시험 페이지로 결제를 한 번 돌린다. 그
      페이지는 최상위로도, 다른 사이트 안의 프레임으로도 연다. 실행이 끝난 뒤 그 출처의 쿠키가 넣기 전과
      같고 다른 저장소가 모두 비었음을 확인한다. 실행 도중 agent-computer를 죽였다 띄워도 같아야 한다.
    - 카드 출처를 기억한 뒤 서버를 다시 띄우고, 그 출처의 그림이 여전히 거절되는지 확인한다.

**구현 메모:**

- 봉투 암호화 — 행마다 데이터 키, 데이터 키는 DB 밖의 키로 감싼다. 지금의 AES-GCM
  (`server/src/credentials.ts`, `KEY_ENCRYPTION_KEY`)이 출발점이다.
- 봉투 암호화는 서버에 두는 로그인 보관함에만 쓴다. 카드는 서버에 없다.
- **저장한 로그인은 사람의 것이고, 그 사람과 함께 지워진다.** 행마다 주인(`users`)을 적고, 계정 삭제
  (`server/src/account/deletion.ts`)가 사용자 행보다 먼저 그 행들을 지운다. 지금의 삭제는 자격증명 중
  `mcp_user_token`만 사람의 것으로 지우므로, 새 보관함을 거기에 넣지 않으면 계정과 브라우저 프로필이
  사라진 뒤에도 비밀번호가 남는다 — 함대의 VM 파기가 늦거나 실패하는 동안 내내. 사람이 계정 메뉴에서
  하나를 지우면 그 자리에서 지운다. `data-lifecycle.md`의 "무엇이 어디에 있는가"·"삭제"에 이 보관함을
  적고, 내보내기에는 값 없이 목록(서비스, 출처)만 넣는다. 카드 출처 기억도 같이 적고 같이 지운다.

**미결:** 출시 전 법률 검토. 범위는 셋이다.
- 서버에 두는 로그인 보관함(개인정보 보호법).
- 우리 앱이 사람의 기기에 카드와 CVC를 저장하는 것. 카드 업계 규칙(PCI DSS v4.0 요구사항 3.3.1.2)은
  승인 뒤의 CVC 보관을 막는다. 리뷰가 인용한 PCI SSC FAQ 1280은 이 컨테이너에서 원문을 확인하지 못했다.
  회사가 값을 갖지 않는 기기 저장이 이 규칙과 여신전문금융업법에 어떻게 걸리는지 확인한다.
- 결제하는 순간 값이 서버를 지나가는 것.

## 7. 직접 조작, 캡챠, 다운로드

- **직접 조작은 PC 앱에서만 한다.** 브라우저와 모바일에서는 하지 않는다. 판정은 화면 너비가 아니라
  Tauri 셸 안인가다(지금은 `isWide`). 셸 여부는 서버가 확인할 수 없는 신호지만 보안 경계가 아니라
  화면 표시다.
- **시범을 보여 가르치기는 PC 앱까지 전부 지운다.** 가르치기는 말로 한다(스킬). 녹화기
  (`server/src/computer/demonstration.ts`, `server/src/live-screen.ts`의 관찰), write-up, 그 라우트와 테스트가
  빠지고, 테스트 하한(`scripts/test-ci.ts`)은 이유와 함께 낮춘다.
- **공동인증서·금융인증서는 하지 않는다.**
- **캡챠:**
  - 승인은 사이트별, 또는 전체. 한 번 승인하면 그 범위에서 봇이 직접 푼다. 상시 허용이므로
    `settleWithoutAsking` 아래에 두고, 누가 언제 정했는지 남긴다.
  - 시도는 3회까지. 넘으면 PC 앱에서는 직접 조작으로, 그 밖에서는 "봇이 못 하는 일"로.
  - 멀티모달 모델을 한 번씩 부른다(봇은 지금 화면을 접근성 트리로만 읽는다). 캡챠 영역만 잘라 보낸다
    — 페이지의 다른 개인정보가 밖으로 나가지 않게.
  - 대상은 이미지 캡챠다. 행동으로 판정하는 캡챠(reCAPTCHA 체크박스, 보이지 않는 캡챠, Turnstile)는
    모델로 풀리지 않는다.
  - 그 모델의 eval이 필요하다.
- **1MB가 넘는 다운로드도 되게 한다**(지금 `laf:download_too_large`, `agent-computer/src/page-watch.ts`).
  상한은 VM 디스크로 정하고, 응답에 싣지 않고 파일로 넘기고, 보관 기간을 `data-lifecycle.md`에 적는다.

## 8. 프로필과 effort

- **프로필 이미지 설정을 지운다.** 프로필 화면의 선택기, 첫 실행의 선택 화면, API의 필드. 얼굴은
  업로드한 그림이 아니라 `avatar_seed`(모양과 색)에서 그린 마스코트다. 그리기와 NOT NULL 때문에 열은
  남긴다.
- 얼굴의 색이 앱 전체의 강조색이다(`app/src/lib/avatar/accent.ts`). 고정 색이 필요하다 — 미정.
- 프롬프트의 "이름과 얼굴은 이 사람이 정했고"(`shared/prompt/base.ko.ts`)가 바뀌면 프롬프트 해시가
  바뀌어 eval 판정을 새로 받는다.
- **effort는 보이지 않고, 사람도 봇도 바꾸지 못한다.** 카드만 숨기면 봇이 `update_profile`로 보이지
  않는 설정을 계속 바꾼다. `BOT_MODEL_EFFORT=false`가 셋을 한 번에 한다: 카드를 숨기고,
  `update_profile`에서 effort를 빼고, 보내지 않는다(모델의 기본값 — Muse Spark에서는 medium).

1. 고정 강조색
2. 카드 저장 화면의 문구("이 기기에만 저장됩니다"처럼 사실 그대로)
3. 백그라운드 브라우저의 동시 상한(측정 후)
4. 위임한 작업의 모델 선택: 역할별 모델, 그리고 판단 모델을 쓸지(처음 제안의 판단 결과 예시 —
   `task`, `complexity`, `reasoning_depth`, `tool_required`, `ambiguity`, `risk`,
   `context_dependency`, `expected_output_tokens`). 쓴다면 연속 점수보다 닫힌 선택지가 낫고(Jev는
   선택지에 확률을 붙인다, `server/src/computer/decision-call.ts`), `risk`는 판단 모델이 아니라 게이트웨이의 일이며,
   메시지를 밖의 판단 모델로 보내는 범위는 first-move가 받은 승인(`server/src/turns/first-move.ts`)을 넘는다.
5. 프로젝트 질의를 프로젝트 대화 기록에 남길지(권고: 남기지 않는다)
6. 루틴의 결과가 프로젝트로 갈 수 있는지
7. 카드 보관의 법률 검토
