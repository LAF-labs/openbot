# 배포 모델 — 결정 기록

결정: 김기범, 2026-08-23. 이 문서는 "어떻게 배포하기로 했는가"와 그 결정이
코드에 갖는 의미를 기록한다. 배포 방식이 바뀌면 이 문서부터 고친다.

## 결정

**Grok Bot 방식.** 유저 1명당 VM 1대를 제공한다. 그 유저가 만든 봇이 몇 개든
전부 그 VM 하나를 공유한다. 봇의 기본값(선탑재 페르소나)은 없다 — 배포는
페르소나를 싣지 않으며(31c307d), 유저가 이름 하나로 봇을 만들어 직접
키워간다(c179b58, 7610f68).

여기서 따라 나오는 **배포 불변식**:

1. **VM 하나에 API 서버 프로세스는 정확히 1개.** 로드밸런서 뒤에 레플리카를
   두지 않는다.
2. **보안 경계는 유저의 VM이다.** 유저와 유저 사이는 VM이 가른다. 한 유저의
   봇들끼리는 VM을 공유하므로, 봇 사이 격리는 유저 내부에서 보장 대상이
   아니다 (컴퓨터·프로파일 분리는 편의이자 감사 단위이지, 경계가 아니다).

## 이 결정이 코드에 갖는 의미

upstream(CopilotKit) 커밋 06a1a84(#21)는 승인 대기표(#15)와 반복
카운터(#17)를 걷어냈다. 이유는 "여러 프로세스에서 조용히 깨진다"였다 —
프로세스 A가 낸 질문을 프로세스 B가 모르고, 카운트가 레플리카 수만큼
쪼개진다.

**우리 배포에는 그 실패 모드가 존재하지 않는다.** 프로세스가 하나뿐이기
때문이다. 따라서 이 저장소의 in-process 설계(승인 대기 Map, repeat 카운트,
gateway 스냅샷 캐시)는 미봉책이 아니라 **이 결정에 의해 옳다.** 코드 리뷰에서
"멀티 프로세스에서 깨진다"는 지적이 나오면 답은 이 문서다.

같은 이유로 upstream 동기화는 **merge가 아니라 선별 cherry-pick**으로 한다.
#21을 머지하면 boundaries의 토대가 삭제된다. 주기적으로 upstream 로그를 훑고
보안·프로토콜 수정만 가져온다.

## 이 결정이 바뀌면 (예: 중앙 멀티프로세스 운영으로 전환)

그때 Postgres 등 프로세스 밖으로 옮겨야 하는 상태 목록:

- 승인 대기 (`server/src/computer/approvals.ts` 계열 — in-process Map)
- repeat 카운트 (`server/src/computer/repeat.ts`)
- gateway 스냅샷 캐시 (upstream도 "next"라고 밝힌 그 캐시)
- 스톨 워치독은 예외 — 스트림을 쥔 프로세스에 있는 것이 맞으므로 그대로 둔다.
